# Schema Comparison Profile

The comparison semantics for deciding whether one JSON Schema can stand in for another (normalization, structural comparison, directional subsumption, and finding suppression), published so independent implementations can produce agreeing verdicts on the same pair of schemas. This is the decision procedure behind interface compatibility checking (implementations are catalogued under [Reference implementations](#reference-implementations)). Conformance here is claimed and versioned independently of core OpenBindings conformance. The core specification defines the document model and does not define schema comparison ([§1, Positioning and scope](https://github.com/openbindings/spec/blob/release/0.2/openbindings.md#1-positioning-and-scope)), so declining this profile implies nothing about OBI conformance, and conforming to the spec requires nothing here.

This is a **semantics profile**, not an operation contract: there is no versioned OBI document beside this README, nothing to invoke, and no canonical `<version>.json` URL. What it publishes is a decision procedure. Its conformance surface is the shared corpus in [`../conformance/comparison/`](../conformance/comparison/), which implementations run unmodified.

**Profile identifier:** `OB-2020-12` (the identifier an implementation stamps on the comparison reports it emits). **Profile version:** 0.1.

**Draft alignment, 2026-09-08:** value equality and numeric ordering follow the exact JSON value model below, not a binary64 serialization. This amends the existing pre-launch profile, not Core or any binding specification. Complete implementation qualification requires both the legacy cases and the exact-value pack; passing an older subset is not evidence of complete conformance to this amended draft. Exact SDK revisions and their qualification evidence are tracked by the OpenBindings project's candidate-cohort process, separately from this profile's authority.

Profile conformance is available to any implementer, not only the OpenBindings Project. A tool that does not claim this optional profile is **not assessed against it**, rather than classified as Core-nonconformant. Reports and test suites distinguish Core/binding conformance, this comparison-profile conformance, and the official SDKs' additional implementation-quality qualification. The profile does not promise value preservation through unrelated parsing, storage, invocation or transforms.

## The question the profile answers

Given a **target** schema (the contract — what an interface declares) and a **candidate** schema (the implementation — what a corresponding operation declares), the profile decides, per direction:

- **Input compatibility** — can the candidate stand in for the target as an *input* contract? The target's consumers may send any value the target admits, so the candidate must **accept at least** everything the target accepts (target ⊆ candidate).
- **Output compatibility** — can the candidate stand in for the target as an *output* contract? The target's consumers rely on the target's shape, so the candidate must **produce only** values the target admits (candidate ⊆ target).

It is not a general-purpose subschema checker: it is scoped to a keyword subset it can decide reliably, and it **fails closed** on everything else (see The profile boundary). A compatible directional verdict establishes inclusion in the stated direction. Where no rule fails and inclusion is not established, the verdict is indeterminate. Comparison is pure and deterministic: no IO, the same verdict on every run and every conforming implementation.

## Schema forms and the unspecified rule

Schemas at operation `input`/`output` positions take JSON Schema 2020-12's two forms:

- **Object form** — compared as described below.
- **Boolean form**: mapped to its equivalent object spelling before comparison: `true` becomes `{}` and `false` becomes `{"not": {}}`. A non-identical root `false` is indeterminate: on the flowing side rule 0a stops, and on the receiving side no in-profile constraint supplies a failure. Identity still holds for these equivalent spellings. The object rule separately recognizes an empty effective member schema.
- **Absent** — an operation that omits a schema leaves that contract **unspecified**. Unspecified is not Top: directional comparison of that slot is *skipped entirely* and reports no finding (see Suppression). Only a *present* schema — including the empty `{}` — is compared. Identical mode is the exception: an absent slot is identical only to an absent slot (see Identical mode, under Suppression), as core §5.1 tells a stated schema from none.

The empty schema `{}` is **Top** ("admits anything"):

| | Target is Top | Candidate is Top |
|---|---|---|
| **Input** | run the other rules with every type flowing; Top alone supplies no failure | compatible, subject to rule 0a |
| **Output** | compatible, subject to rule 0a | run the other rules with every type flowing; Top alone supplies no failure |

## The profile boundary

The profile compares exactly these keywords (**in scope**):

```
$ref  $defs  allOf  oneOf  anyOf
type  enum  const
properties  required  additionalProperties  items
minimum  maximum  exclusiveMinimum  exclusiveMaximum
minLength  maxLength  minItems  maxItems
```

These keywords are **annotations**: they never affect a verdict and are stripped during normalization:

```
title  description  examples  default  deprecated  readOnly  writeOnly  $comment
$schema  format  discriminator
```

(`format` is an annotation, not a structural constraint. Annotation stripping applies to 2020-12 schema positions. Schemas an OBI document contains are read as 2020-12 even if a declaration violates OBI-09; positions in a document that is not an OBI document, and externally reached positions, follow their assigned dialect under Normalization.)

`nullable` is OpenAPI 3.0's spelling, not a JSON Schema 2020-12 keyword: core §5.5 reads it as an unknown keyword, so `{"type": "string", "nullable": true}` admits no `null`. The profile gives it no meaning of its own. It is outside the profile and follows rule 0a, including the distinction between flowing and receiving sides. A kind that reads OpenAPI 3.0 converts `nullable: true` to a `type` union with `"null"` when it projects a schema, so the schemas it writes are 2020-12 schemas.

Keys prefixed `x-` are extensions and are stripped.

**Everything else fails closed, at positions that differ.** A schema using any other keyword (`pattern`, `not`, `if`/`then`/`else`, `patternProperties`, `multipleOf`, `uniqueItems`, `prefixItems`, ...) is *outside the profile* at that position. Normalization retains the keyword and marks the position. Identity runs first. At a non-identical position, an outside-profile keyword on the flowing side stops the walk there with indeterminate. Where outside-profile keywords occur only on the receiving side, its in-profile rules run with the exclusions in rule 0a; the position is incompatible if an eligible rule fails, otherwise indeterminate, never compatible. Consumers surface indeterminate distinctly from compatible and incompatible.

`items` is compared as 2020-12 `items`: one schema applied to every element when `prefixItems` is absent. Beside receiving `prefixItems`, the `items` rule is skipped under rule 0a.

## Normalization

Comparison operates on **normalized** schemas. Two normalized schemas are structurally identical when their values are equal under the exact value rules below, except that arrays at schema `oneOf`/`anyOf` keyword positions compare as multisets of structurally identical normalized variants: order is irrelevant, multiplicity is retained. This exception applies only at schema keyword positions, never inside `const` or `enum` instance data. It does not identify a `oneOf` schema with an `anyOf` schema. No canonical byte serialization is required, and structural identity is not general schema equivalence.

Every schema position an OBI document contains is read as 2020-12, with `$schema` having no other effect there and any other declared value violating OBI-09. For a position outside an OBI document reached from it through an external URI, including a fragment, descendant or embedded resource, retain as outside-profile context the dialect JSON Schema assigns that position, whether explicitly declared or inherited. When that assigned dialect is not 2020-12, do not perform 2020-12 reference-sibling or merge rewrites or receiving-side projection there: only identity of the schema, its assigned dialect and its entire supplied resource context can prove compatible, and otherwise the position is indeterminate on either side. This is the externally assigned dialect rule.

A schema in a document handed to comparison that is not an OBI document keeps the dialect JSON Schema assigns it: the `$schema` declared at the root of its schema resource or inherited from an enclosing resource, or 2020-12 where none is declared. Each position within that document, and each position reached from it, takes its dialect the same way. A position under a member that the enclosing resource's dialect does not define as a keyword, reached by a JSON Pointer, still lies within that resource and takes its dialect. Where the dialect is not 2020-12, the externally assigned dialect rule applies. How a tool recognizes an OBI document is tool policy.

The following normalization steps apply to 2020-12 positions.

Map Boolean schemas to their equivalent object spellings at every schema position before step 3 tests whether the compared subtree contains retained content, including positions outside `$defs`. This is not a transformation of Boolean instance data, and it makes both Boolean/object spellings undergo the same retention test and normalize alike. Steps, in order:

1. **Profile keyword marking.** Any key that is not in scope, not an annotation, and not `x-`-prefixed is retained, subject to the schema-position normalization in step 9, and marks the schema as outside the profile at that position. The refusal is deferred to comparison, where the identity rule runs first (see The profile boundary). After unwrapping a sole branch as step 4 specifies, an `allOf` whose sibling keywords or any branch carry an outside-profile keyword is not merged: the branches are normalized individually and the `allOf` array is retained in authored order, so identity remains decidable and a non-identical comparison at that position is indeterminate with no later rule run (rule 0a). The same holds for an `allOf` in which a branch, or the sibling keywords, sets `additionalProperties` to `false` or a schema while another branch, or the siblings, declares a property that branch does not: merging would let the other branch's property past the closed branch, which the original forbids, so the branches are retained as authored. It holds too for an `allOf` with `oneOf` or `anyOf` in a branch or among its sibling keywords, written inline or carried by a resolved `$ref`: no merge rule covers a union.
2. **`$ref` inlining.** A `$ref` is resolved and its (normalized) target conjoined with the referencing schema's other keywords, as JSON Schema 2020-12 applies `$ref` beside its siblings: a schema carrying `$ref` and other keywords normalizes as an `allOf` of the target and those keywords, merged under the `allOf` rules (step 4), and a `$ref` alone is equivalent to inlining its target. A reference resolves as core §7 resolves it: against the base of the schema resource that contains it, so a fragment-only reference inside a schema that declares `$id` resolves within that resource, and one in a schema without `$id` (`#/schemas/Foo`) against the document root the caller supplies (in OpenBindings use, the interface document — named schemas live in the document's top-level `schemas` map). External refs resolve only if the caller supplies a fetcher, relative refs only against a caller-supplied base; otherwise resolution fails. Reference **cycles** are detected and fail — the profile does not compare recursive schemas.
3. **Stripping.** Annotations and `x-` extensions are removed at schema positions, including within retained applicators and kept definitions as step 9 specifies. `$comment` is an annotation; its text never changes a verdict. `$defs` is removed after references are inlined unless the schema's own subtree carries a keyword retained outside the profile (`$dynamicRef`, `$anchor`, `$dynamicAnchor` or any other), in which case it is kept so identity compares what that keyword could depend on. The exact empty schema, a schema whose content after Boolean mapping and stripping is exactly `{"not": {}}`, whether authored or mapped from `false`, does not by itself keep `$defs`: it can depend on no definition. Other retained content in the subtree still keeps it, and rule 0a and the root-`false` rule are unchanged. A retained keyword elsewhere in the resource does not keep it: a reference leaving the compared schema is compared by its target (step 9). Kept `$defs` supplies identity context, never a constraint or keyword of the compared position; disregard it in every directional rule and in that position's outside-profile test. A schema whose only content is kept definitions is Top.
4. **`allOf` flattening.** Each branch is first normalized in full: these steps apply recursively, so a `$ref` branch is resolved and profile-checked exactly as step 2 requires, and a nested `allOf` inside a branch flattens before its parent merges. An `allOf` with exactly one normalized branch and no remaining sibling constraints or identity context normalizes to that branch, even when the branch is a union or carries retained content; its references must already have been resolved in their original scope. Otherwise the schema's own sibling keywords (everything beside `allOf` that survives stripping) form one additional branch. All normalized branches then merge into a single schema (rules below): the sibling branch first, then the declared branches in order. The order is observable: an `enum` intersection emits each surviving exact instance value once, in the order of its first occurrence in the first branch that declares `enum`. This includes an `allOf` merge with only one `enum`-bearing branch; repetitions in any branch add no occurrences. An `allOf` step 1 retains is not merged. The enum-intersection rule still applies to a sole enum-bearing branch: singleton unwrapping does not bypass its de-duplication. The merged result is normalized again.
5. **Canonical `type`.** A scalar `type` becomes a one-element array; arrays are deduplicated and sorted.
6. **Canonical `required`.** Deduplicated and sorted.
7. **Recursion.** `properties` values, `additionalProperties` (schema form), and `items` are normalized recursively.
8. **Union variants.** Normalize `oneOf`/`anyOf` variants recursively. Retain their authored order for traversal and diagnostic indexes; structural comparison ignores variant order as described above. Sorting by serialization is not an equality test.
9. **Retained schema content and references.** At schema positions inside retained applicators and kept definitions, apply Boolean mapping, annotation and `x-` stripping, and canonical `type` and `required` normalization; preserve the retained applicator itself and its authored array order. Instance data inside `const`/`enum` and unknown-keyword payloads remains verbatim. A `$ref` at a subschema position of a retained JSON Schema 2020-12 applicator (`not`, `if`, `then`, `else`, `dependentSchemas`, `prefixItems`, `contains`, `patternProperties`, `propertyNames`, `unevaluatedItems`, `unevaluatedProperties`), and a retained `$dynamicRef` taken at its initial target, is resolved as step 2 resolves references but not inlined: the keyword stays as authored. Two schemas whose retained content is otherwise identical are structurally identical only when each such reference resolves, on each side, to structurally identical normalized targets. A reference that cannot be resolved, or a cycle reached through such references, fails the comparison as step 2's failures do. A `$ref` member inside a keyword that is not a 2020-12 applicator is data and compares as written.

Outside the named normalization rules, arrays retain authored order and multiplicity. In particular, an `enum` array not synthesized by an `allOf` merge is not reordered or deduplicated for structural identity; arrays inside `const` or `enum` instance values and unknown-keyword payloads remain ordinary ordered arrays. Canonical `type` and `required`, and the schema union-array identity exception, retain only their stated scope.

### Exact values, ordering and capability failures

The value model and instance equality are those of [JSON Schema 2020-12 Core §§4.2.1–4.2.2](https://json-schema.org/draft/2020-12/json-schema-core#section-4.2.1): types remain distinct; numbers compare by mathematical value; strings by code points; arrays item by item in order; and objects by their unordered members. Missing members differ from present null values. Numeric spelling is not identity: `1`, `1.0` and `1e0` are equal, as are positive and negative zero. Adjacent integers or decimals remain different even when a binary64 conversion would collapse them.

These rules apply recursively to instance values in `const`/`enum`, their sets and intersections, and normalized structural identity. Numeric bounds and string/array counts are ordered by their exact mathematical values, including bound selection during `allOf` merging. No rounding, overflow clamping, underflow-to-zero, conversion to strings, or exposure of a host numeric wrapper as a JSON object may decide equality, ordering or compatibility. This specifies comparisons, not an arithmetic language or a required host representation.

[RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785) remains useful for eligible serialization tasks, but its narrower numeric domain does not bound this profile's values. JCS unavailability is neither inequality nor a proof of equality, and two serialization failures must never compare equal. A hash or serialization key may accelerate a decision only when it cannot erase relevant value distinctions and the required exact comparison is retained.

A processor unable to retain or compare an input exactly must report an explicit implementation-capability/resource failure without asserting a comparison verdict for altered data. It must not call supported numeric data an outside-profile keyword case. A fixture requiring a definitive verdict remains an unmet profile capability if the implementation refuses it; that is not, by itself, a Core conformance failure. Practical limits must be reported rather than silently changing values, and this rule does not require expanding huge exponents into unbounded digit strings. The existing outside-keyword `indeterminate` and the normalization errors (reference cycles and resolution failures) remain distinct.

### `allOf` merge rules

| Keyword | Rule |
|---|---|
| `type` | intersection; `integer` is a subtype of `number` (`number` ∩ `integer` = `integer`); an empty intersection is an unsatisfiable merge (below) |
| `properties` | union of keys; overlapping keys merge recursively |
| `required` | union |
| `additionalProperties` | any branch `false` wins; schema forms merge recursively; schema overrides `true`; applied only where every branch that constrains it declares the same property names as the merged result (otherwise the `allOf` is retained, step 1) |
| `enum` | intersect the sets of exact instance values; emit each surviving value once, in first-occurrence order from the first branch that declares `enum`; an empty intersection is an unsatisfiable merge (below) |
| `const` | equal values merge; conflicting values are an unsatisfiable merge (below) |
| `items` | recursive merge |
| `minimum` `exclusiveMinimum` `minLength` `minItems` | most restrictive (highest) wins |
| `maximum` `exclusiveMaximum` `maxLength` `maxItems` | most restrictive (lowest) wins |

An **unsatisfiable merge** (an empty `type` or `enum` intersection, or conflicting `const` values) means no value satisfies the merged schema at that position. At any position, the compared schema itself included, the merge normalizes that position to `{"not": {}}`, the exact empty schema, in place of everything it produced there. A property member it replaces may then not appear, an array whose `items` it replaces may then hold no element, a union variant it replaces then contributes nothing, and a compared schema it replaces admits nothing. Comparison then treats that position as any `{"not": {}}`: the object rule recognizes an empty member, a compared schema compares as a root `false` does (identical to itself, otherwise the root-`false` rule under Schema forms), and elsewhere rule 0a applies. An unsatisfiable merge is not an error: reference cycles and resolution failures are the only normalization errors.

## Directional subsumption

The **flowing side** is the target for input and the candidate for output. The **receiving side** is the other side. Absent keywords are unconstrained unless a rule below says otherwise. Every relevant member and later rule contributes before the position's verdict is taken: incompatible dominates indeterminate, which dominates compatible. An unresolved comparison does not hide a later eligible failure. Names, authoring order and rule order may choose a reason, never a verdict.

**Incompatible.** Some value flows and is refused, unless the flowing schema is vacuous where the counterexample needs a value: it allows a type, requires a property or needs an item for which it accepts nothing. The profile makes no general vacuity decision: its local empty-member rule and stated failure guards still apply, but their local conclusions do not by themselves decide the enclosing schema's verdict. The exception includes a required member already recognized as empty; an independent failure still decides unless an express guard withholds it. Across members and later rules, a failure decides.

An **eligible failure** is a failure of an applicable rule that has not been replaced by indeterminate by a stated guard or boundary and that meets the incompatible definition. The directional incompatible promise concerns schema values. Identical mode's incompatible means different normalized structure, and an unmatched target operation is a correspondence failure; neither asserts a value counterexample.

### Rule order

0. **Identity.** Structurally identical normalized sub-schemas are compatible, whatever keywords they carry; the walk does not descend. A schema always stands in for itself. Externally assigned dialect and resource context participate as specified under Normalization.
0a. **Boundary.** At a non-identical position, `oneOf` on either side makes the position indeterminate, including a receiving `oneOf` with a branch covering the flowing schema; no later rule or sibling constraint runs at that position. A non-identical position carrying retained `allOf` on either side is also indeterminate and no later rule runs there. An outside-profile keyword on the flowing side likewise makes the position indeterminate and no later rule runs there. With outside-profile keywords only on the receiving side, compare its in-profile constraints, but skip every use of its `additionalProperties` beside `patternProperties`, including effective-member fallback, and skip its `items` beside `prefixItems`. A skipped obligation is unresolved. Such a position can be incompatible or indeterminate, never compatible. The externally assigned dialect boundary under Normalization applies on either side without receiving-side projection.
1. Top rules (below)
2. `type`
3. `const` / `enum`
4. object rules (`required`, `properties`, `additionalProperties`)
5. array `items`
6. numeric bounds
7. string bounds (`minLength`/`maxLength`)
8. array bounds (`minItems`/`maxItems`)
9. unions (`anyOf` only)

The type-specific rules run only for types the flowing side allows, using declared `type` and all types when it is absent. In-profile constraints applying only to other types cannot supply either a failure or an unresolved obligation; outside-profile content still follows rule 0a even when it appears inapplicable to the flowing type. The order selects a diagnostic among findings carrying the final verdict; it does not authorize stopping at the first non-compatible result. Boundary stops run first. The length-domain rule's emptiness facts apply before any type or length failure. Receiving Top is checked before union coverage.

At a position carrying flowing `const` or `enum`, a failure of a rule other than `const`/`enum` is indeterminate: a type, bound or member failure may concern values that the finite constraint excludes. A failure from any rule at a position carrying flowing `anyOf` is indeterminate unless the union counterexample rule establishes the same failure for the whole flowing position. Pairwise compatible coverage still contributes its inclusion proof.

### Per-keyword rules

**Top.** A normalized empty object, including mapped `true`, is recognized as Top. Kept definitions do not constrain it. A receiving schema containing only an all-types `type`, empty `properties`, empty `required`, and unconstrained `additionalProperties` or `items` is also Top for directional comparison; any subset of those members is sufficient, with absent type meaning all types. An all-types declaration contains `array`, `boolean`, `null`, `number`, `object` and `string`; `integer` is optional because `number` includes it. Here an unconstrained `items` or `additionalProperties` is `true` or a nested schema recognized as Top by this paragraph, applying the same test recursively. These equivalences do not remove an outside-profile obligation. After rule 0a, receiving Top proves compatible and ends the position before union coverage, including for a flowing `anyOf`. A flowing Top alone never supplies an incompatible result: run the other rules with every type flowing. If the receiver is not recognized as Top, this Top rule contributes indeterminate. An eligible later failure can decide incompatible, but passing later tests does not discharge this obligation except where a positive proof below expressly does so.

**`type`.** A missing `type` means all types on either side, including beside receiving `const` or `enum`. Every flowing type must be allowed by the receiving side; `integer` is covered by `number`. The length-domain rule removes obligations for types whose length domains are empty. Where the flowing side carries `const` or `enum`, failure of this type test is indeterminate, not incompatible. A type failure of `number` against `integer` is indeterminate only when the effective flowing bounds admit at most one number, meaning that both endpoints exist and the lower endpoint is greater than or equal to the upper endpoint, with exclusivity determining whether the equal-endpoint interval is empty or a singleton. Passing this test alone does not prove the position compatible.

**`const` / `enum`.** Values compare by exact instance equality. Every value listed by the flowing `const` or `enum` must be admitted by the receiving `const` and `enum`; a receiving side with neither is unconstrained by this rule. A failure based on an authored flowing value is eligible only if that value satisfies the flowing `type`, `const` and `enum` together and no other keyword at the flowing position could refuse it; otherwise that failure is indeterminate, and this does not prove inclusion by removing excluded values. Judged for each authored value, only two kinds of keyword cannot refuse it: one the Top rule treats as unconstrained (an all-types `type`, empty `properties` or `required`, or an `additionalProperties` or `items` that is `true` or recognized as Top), and one that applies only to JSON types other than the value's own (`minimum`, `maximum`, `exclusiveMinimum` and `exclusiveMaximum` apply only to numbers; `minLength` and `maxLength` only to strings; `items`, `minItems` and `maxItems` only to arrays; `properties`, `required` and `additionalProperties` only to objects). Any other keyword at the flowing position could refuse it, and outside-profile content on the flowing side still stops the position under rule 0a. Where the flowing side has neither `const` nor `enum`, a receiving finite restriction supplies a failure only if the flowing position has no constraints other than `type` and permits at least one of string, number, integer, array or object; otherwise that obligation is indeterminate. This rule does not prove acceptance by a different receiving keyword; the finite inclusion proof below can.

**Finite inclusion.** Where rule 0a neither stops the position nor rules out a compatible verdict there, and the flowing side carries `const` or `enum`, the flowing values are the values those keywords allow: with one of the two, each value it lists; with both, the `const` value if the `enum` lists it by exact instance equality, and otherwise none. No value is removed for failing another flowing keyword. The position is compatible when the whole receiving schema accepts each flowing value, and so when no value flows. Acceptance is decided by applying the receiving in-profile keywords to the exact value under the value rules above. `type` accepts a value whose JSON type it lists, with `integer` accepting a number whose fractional part is zero; `const` and `enum` accept by exact instance equality; numeric bounds compare exact mathematical values; `minLength` and `maxLength` count the string's Unicode code points, as JSON Schema counts string length; `minItems` and `maxItems` count the array's elements; `required` needs each named member present. Each member of an object value is tested against its `properties` entry, otherwise against `additionalProperties`; each element of an array value is tested against `items`; an `anyOf` accepts when at least one variant accepts. An absent keyword, or one that applies only to other JSON types, accepts the value; kept definitions are disregarded. Outside-profile content, `oneOf` and retained `allOf` keep their boundaries: a schema applied to a value does not accept it when that schema itself carries a keyword outside the profile, has an assigned dialect other than 2020-12, or carries a `oneOf` or a retained `allOf`; where that schema is an `anyOf` variant, another variant may still accept the value. When the test accepts every flowing value, inclusion is proved and ends the position: no other rule contributes there. A refused value does not by itself make the position incompatible; the `const`/`enum` rule above still governs failures.

**Objects.** The receiving side's `required` must be a subset of the flowing side's. For every name declared by either side, each side's effective schema is its `properties` entry when present, otherwise its `additionalProperties`, with absence meaning `true`. Compare these effective schemas in the flow direction; also compare the two `additionalProperties` schemas for all remaining names. This applies in both directions. An effective member schema `false` or `{"not": {}}` admits no member value: an empty flowing member or unconstrained receiving member discharges that member obligation; an unconstrained flowing member against an empty receiving member fails it; other pairs recurse. The receiving `patternProperties` exclusion in rule 0a still applies. Recognizing a required member as empty does not by itself discharge the whole object or withhold an independent failure under the incompatible definition.

**Array `items`.** Compare item schemas recursively in the flow direction; absence contributes Top. If flowing `maxItems` is zero, discharge the items inclusion obligation without comparing item schemas; other obligations and boundaries still run. No items failure at such a position is eligible.

**Numeric bounds.** `minimum`/`exclusiveMinimum` combine into the stricter lower bound, and `maximum`/`exclusiveMaximum` into the stricter upper bound. At equal values an exclusive lower bound is higher and an exclusive upper bound lower than an inclusive one. The receiving interval must be at least as wide as the flowing interval. A missing bound is unconstrained. A numeric-bound failure when the flowing side allows `integer` but not `number` is indeterminate unless the relevant flowing endpoint is absent, both relevant endpoints are inclusive integers, or the same integral endpoint is included by the flowing bound and excluded by the receiving bound. These exemptions remove only this endpoint guard, not any other eligibility condition.

**String/array length domains.** Compare string and array bounds as sets of nonnegative integral lengths, with absent minimum zero. The receiving length set must contain the flowing length set. A receiving schema whose only constraints are such bounds admitting every nonnegative length discharges the Top obligation. Test emptiness before a type or length failure: if every type the flowing schema can admit at that position is excluded by these length constraints, inclusion is proved and ends the position, subject only to rule 0a; otherwise an empty length domain discharges only that type's obligations at that position, and no failure at that position may require a length in that domain. A compatible verdict still requires that rule 0a permits it. In particular, an absent minimum cannot supply a negative-length counterexample against a receiving minimum of zero.

**Unions.** Compare `anyOf` with `anyOf`; for coverage when exactly one side has `anyOf`, read the other whole schema as a union of one. This view does not remove constraining siblings. Each flowing variant must have at least one compatible receiving counterpart for coverage to prove inclusion. Every receiving union sibling must also be proved against the whole flowing schema; its eligible failure can decide incompatible even when coverage is unresolved. A non-union receiver is already compared in full as the sole counterpart: successful coverage discharges all its constraints without a second failing comparison of the union's nominal missing type. Successful coverage and all receiving sibling proofs discharge the Top obligation as well. Flowing siblings only narrow a variant's possible values; they do not invalidate a positive coverage proof. If a variant has no compatible counterpart, the coverage obligation is indeterminate unless the counterexample rule below applies. Different counterpart failures need not refuse the same value. The verdict does not depend on authored order.

**Union counterexamples.** An uncovered flowing variant can supply incompatible by either of two tests: an eligible failure against the sole receiving counterpart; or a flowing type excluded by every counterpart's declared type, with the flowing variant's failure eligible under the incompatible definition. Conjoin the flowing siblings' in-profile constraints with the variant; the evidence stands if the conjoined variant still has that eligible failure. Permit no counterexample through a boundary that would stop the counterpart comparison. Without such evidence, keep the obligation indeterminate. These tests are the only exception to the flowing-`anyOf` failure rule above; they do not enumerate instances or combine unrelated pairwise failures. An eligible union failure dominates other unresolved variants, otherwise an unresolved variant makes the union obligation indeterminate, otherwise coverage succeeds.

## Verdicts and findings

A single directional check returns compatible, incompatible or indeterminate, with a reason for a non-compatible result. The reason names a finding carrying the final verdict, prefixed by its deciding keyword and, for nested findings, its path:

```
type: candidate does not allow "number"
required: candidate requires "extra" but target does not
properties["count"]: type: candidate does not allow "integer"
items: enum: candidate value "c" not in target enum
additionalProperties: target forbids but candidate allows
```

Reason strings follow these conventions, so independent implementations render them alike:

- **Unresolved failures.** An indeterminate result caused by an ineligible failure retains that failure's located keyword in its reason and states why the failure is unresolved; an actual boundary stop names `outside-profile`. Diagnostic choice does not change the verdict.

- **Deciding keyword.** The prefix names the deciding rule or boundary. In mixed `const`/`enum` rejections it names the receiving keyword: the candidate's on input and the target's on output. A declared property rejection names its own `properties["…"]` path.
- **Values render truthfully.** Interpolated values use a JSON representation of the exact value, with quoted/escaped strings and no numeric approximation. Equivalent numeric spellings are permitted; JCS-style rendering may be retained where it preserves the value. Rendering is diagnostic, not the equality algorithm. A bounded diagnostic may identify an omitted value by location rather than print a rounded substitute; inability to render a full value must not manufacture a verdict.
- **Exclusive bounds are marked** (`minimum: candidate minimum exclusive 0 is greater than target minimum 0`).
- **Unions carry the real key and authored index** (`anyOf: target variant 1 has no compatible candidate variant`).
- **Deterministic member choice.** Choose among findings carrying the final verdict, in the stated rule order. Types, properties and required names use their lexicographically first such member; enum values and union variants use their first such authored element. Implementations must not let member names, authoring order or map iteration change the verdict.

Reason strings are diagnostics for humans; the verdict is the interoperability surface. Independent implementations are expected to agree on the deciding keyword prefix; the corpus's profile assertions check verdicts. An implementation may hold its own exact reason strings in its own tests, and the exact-value pack's separately labelled diagnostic assertions are such a bar. Neither narrows profile conformance: every implementation is held only to the deciding-keyword floor above.

**Interface-level checking** folds directional checks over two documents: for each operation the required interface declares, the provided interface is searched across its flat key+aliases namespace ([core §5.1](https://github.com/openbindings/spec/blob/release/0.2/openbindings.md#51-operations)); a missing operation is a `missing` issue; for each matched pair with both schemas present, output is checked (provided output must satisfy required output) and input is checked (required input must be acceptable to provided input), yielding `output_incompatible` / `input_incompatible` issues whose detail carries the engine's reason. Issues appear in sorted operation-key order — never the document's declaration order — with the output issue before the input issue for a matched pair.

**Verdict vocabulary and collapse.** Consumers that summarize many per-operation outcomes into one verdict use three values with dominance

```
incompatible  >  indeterminate  >  compatible
```

Preserve individual operation and slot outcomes when producing a summary. An empty or entirely skipped set of directional checks summarizes to compatible. Any incompatible outcome makes the summary incompatible; otherwise any indeterminate outcome makes it indeterminate; otherwise it is compatible. A removed operation counts as incompatible; an added operation is compatible.

## Suppression

The profile deliberately reports **no finding** in these situations:

- **Unspecified schemas.** In directional comparison, when either side of a pair leaves a slot's schema absent, that slot's comparison is skipped entirely. Unspecified is a statement of "no contract declared", not an empty contract. Identical mode does not skip it (below).
- **Annotations and extensions.** Differences confined to annotation keywords or `x-` extensions never produce findings (they are stripped before comparison).

Consumer-level *finding suppression* — downgrading a reported finding by rule, with an audit trail — is a consumer policy on top of the report and is outside this profile.

**Identical mode.** Whole-document identity (the corpus's `identical` mode) compares normalized schemas structurally, outside-profile keywords included: identical documents are compatible and differing documents are incompatible, with the first differing keyword as the finding. Identity never yields indeterminate, because sameness is decidable for any keyword once both sides normalize (a reference cycle or a resolution failure fails normalization, the third outcome, as an error and not a verdict; an unsatisfiable merge normalizes to `{"not": {}}` and compares like any other schema). An absent slot is identical only to an absent slot: a pair where one side states a schema and the other states none differs, with the finding `unspecified`, since core §5.1 distinguishes a stated schema, even `{}`, from none.

## Conformance corpus

The shared corpus lives at [`../conformance/comparison/`](../conformance/comparison/): a `manifest.json` plus fixture files in four categories (`profile/`, `structural/`, `subsumption/`, `suppression/`), and the manifest's `exactValues` pack carrying JSON-text documents so fixture decoding cannot round their numbers. Both packs test this same profile, not different precision modes. Implementation harnesses consume the corpus unmodified (locate convention: `OB_INTERFACES_CORPUS`, else the sibling-checkout path; see [`../conformance/README.md`](../conformance/README.md)). Where this prose and the corpus disagree, the prose governs. Implementation gaps must remain visible; a partial passing run is not whole-profile qualification.

Supplemental [external-resource cases](../conformance/comparison/external-resources.md) give exact supplied resource contexts and dialect expectations, including documents handed to comparison that are not OBI documents. Fixture format 1.0 has no supplied-resource carrier and embeds only OBI documents, so these cases are prose vectors outside the manifest.

## Reference implementations

- Rust SDK: the `openbindings-schema-comparison` crate (`compare` and `identical` for schema pairs, `check_interface` for the interface-level fold)
- `ob compat`: comparison reports (`ob-comparison-report/v1`) stamped with this profile's identifier, layering a structural walk, graded finding kinds, and suppression rules on the same engine
